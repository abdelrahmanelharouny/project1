Data Governance & Provenance — the Data Passport Model
Four control layers ensure every number shown to a decision-maker can be traced, reproduced and defended
Layer 1 · Input provenance
nothing enters untracked
Source registry
Every external dataset is registered with origin, license and update cadence before ingestion. data_sources · dataset_products
Ingestion audit
Each data load is tracked end-to-end — schedule, status, row counts and failures. ingestion_jobs
Observation quality flags
Manual and sensor observations carry explicit quality flags; flagged data never silently enters analysis. observation_quality_flags
Layer 2 · Baseline integrity
the truth cannot be edited
Immutable field state
The authoritative field baseline is content-locked with a checksum — any change produces a new state, never a modification of history.
Append-only validation
Scenario validation history is append-only; corrections arrive as new records, never as overwrites.
Layer 3 · Scenario governance
evidence classes enforced by the database
Evidence-class binding
Each scenario type is bound to an evidence class — observed, hypothetical, or not_available — enforced by database constraints.
Lineage protection
Restricting foreign keys preserve the parent–child chain from the baseline to every derived scenario; lineage cannot be severed.
Finality triggers
Finalized scenarios are frozen by database triggers — and a scenario whose evidence class is not_available can never be finalized.
Layer 4 · Honest output
uncertainty is published, not hidden
“Unknown” policy
A missing capability is reported as unknown — never disguised as poor health, zero risk, or a fabricated estimate.
Twin validation
Model predictions are continuously checked against observed reality; divergence is measured and reported, not hidden.
Requirements ladder
Every comparison records which data requirements were satisfied, partially met, or missing — so conclusions carry their own caveats.
The Data Passport — issued with every result
A machine-readable companion that travels with each output, answering the reviewer’s questions before they are asked:
data provenance — where each input came from completeness — what is present and what is missing engine versions — exactly which code produced the numbers honest gaps — capabilities not yet available
