# CropTwist — Master Gap Analysis and Roadmap Matrix

**Updated:** 2026-11-14
**Baseline:** `main` at `01f9fa2524a71a1bee40e523b729e4c73f6d37d9`; current worktree includes the improvements listed under “Current batch.”
**Interpretation:** status refers to inspected source and executed local checks. It does not imply current CI, browser, production, or external-provider success.

## Status and priority definitions

- **Implemented / source-reviewed:** code was inspected and the capability exists; runtime may remain unverified.
- **Partial:** meaningful code exists but material requirements are missing or inconsistent.
- **Incorrect / security gap:** an inspected path can violate its stated contract or safety boundary.
- **Missing:** capability was not found in the audited first-party scope.
- **Externally blocked:** code may exist, but user-provided credentials, accounts, infrastructure, or approved spending are required for live validation.
- **P0:** stop-ship configuration/security risk; **P1:** correctness, authorization, or evidence-trust risk; **P2:** important integration/UX/scalability gap; **P3:** lower-risk polish/localization.

## Dependency-aware implementation roadmap

### Phase A — Close foundational release risks

1. Complete auth/entitlement bypass fixes and fail-safe production configuration. The current batch addresses logout-family invalidation and Compose prefix/readiness configuration only.
2. Import all current ORM modules into Alembic target metadata; assert P2/P3 constraints and run the migration sequence on disposable PostGIS.
3. Correct observation transaction/numeric/CSV/coverage contracts and the direct HLS field-window/Fmask path before widening satellite data claims.
4. Make queue/domain job states consistent and recovery replayable; explicitly document single-process deployment until shared claims exist.

### Phase B — Make agricultural and AI conclusions match evidence

1. Correct version/region/temporal alignment in knowledge, suitability, rotation, stress and decision comparison.
2. Finish a single evidence-safety contract for Q&A, briefs, and narratives; make numeric/unit validation fact-bound and harden prompt data encoding.
3. Add tests for incomplete evidence and unsafe model/provider behavior using deterministic fakes; do not rely on live LLM assertions.

### Phase C — Integrate frontend and release confidence

1. Add shared organization selection, clear async query states, bounded auth retries, and RTL/logical direction fixes.
2. Extend rendered/browser/accessibility tests beyond helper tests; run the existing Next.js build/lint/typecheck and browser flows in a safe local environment.
3. Validate report field ownership/deletion behavior and report provenance.

### Phase D — Verify external readiness and production operations

1. Provision target PostGIS, storage, worker, secrets, TLS ingress, monitoring and backup/recovery services.
2. Run live, authorized provider and model smoke tests and record last-success times; never infer this from source or fixture tests.
3. Validate multi-process behavior or formally keep the first production topology single-process; establish backup restore, metrics retention and incident recovery.

### Phase E — Add optional strategic capabilities only when justified

1. Decide whether RAG, model-selected tools, multi-provider routing, or a trained predictive model solves a measurable user need.
2. For each approved capability, define source/permission/evaluation contracts before shipping it.
3. Do not present RAG or ML as complete until their retrieval/training/evaluation criteria are satisfied.
