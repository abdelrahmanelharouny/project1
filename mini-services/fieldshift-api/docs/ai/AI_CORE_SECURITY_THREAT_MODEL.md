# AI Core Security Threat Model

**Scope:** Authenticated `/api/v1/ai` request/discovery/conversation/feedback/knowledge routes, deterministic orchestration, the existing advisor, provider adapters, transcript ownership, execution traces, and bounded retention. The Core is field-scoped and read-only; it is not a general autonomous agent. This document describes code controls and residual risk, not a completed security certification or production approval.

## Assets and trust boundaries

| Asset | Security interest |
|---|---|
| Farm/field, soil, water, climate, rotation, vegetation, and spatial evidence | Tenant-sensitive data; no read before server-side field authorization. |
| Questions, conversation history, model output, and knowledge text | Untrusted/private text; prompt injection, data exposure, and unsafe attribution risks. |
| Session owner, user, organization, farm, and role | Access-control decisions must be derived from authenticated principal and database, not client/model. |
| Provider credentials and model requests | Server secrets and possible external processing of sensitive context. |
| Tools and domain results | Bounded, registered, permission-checked, side-effect-free operations. |
| Traces, transcripts, and feedback | Traces are metadata-only; transcripts and consented feedback contain user content and require restricted access/retention. |
| Rights-attested knowledge documents and vectors | Licensed, organization-scoped material; processing or embedding may disclose content to separately configured providers. |

Trust boundaries: client → authenticated CropTwist API; client-selected field/domain → server resolver; database evidence → untrusted model context; model response → validators; deterministic plan → tool registry; CropTwist → configured remote provider; user/knowledge content → embedding adapter; transcript/feedback → metadata-only operational trace.

## Threats, implemented controls, and residual risk

| Threat | Current controls | Residual risk / required follow-up |
|---|---|---|
| Forged actor, tenant, field, or tool selection | Strict request schemas reject extra identity/tenant fields. `get_principal` supplies the user; `get_field_for_principal` authorizes the supplied field; farm, organization, and role are derived server-side. The deterministic planner and registry allowlist tool names. | Existing identity policy grants active organization members field reads and has no per-domain ACL. Do not represent `field.read`/`field.analysis.read` as role-specific soil/climate grants. |
| Cross-tenant field access | Field membership is verified before evidence builder/tool calls. A supplied field is authorized even if the requested capability is unavailable. | Verify in disposable-database integration tests. Repository-level code review does not establish deployment configuration or database state. |
| Cross-user or cross-field conversation disclosure | Core sessions are stamped with `owner_user_id`; reuse requires the same owner and authorized field. Missing, expired, legacy owner-null, cross-field, and another user's session share the same 404. Conversation listing/history is owner-scoped. | Legacy advisor routes retain historical field-scoped behavior for owner-null sessions. Core does not reuse them. Confirm legacy policy and deployed migration state. |
| Prompt injection or untrusted-data breakout | Question/history/evidence are treated as untrusted content; existing guard sanitizes and escapes delimiters; history length and roles are bounded; model cannot set tool/identity/resource IDs. | Escaping is defense in depth, not semantic isolation. Prompt-injection signals or labels do not prove resistance. New source types require adversarial tests. |
| Arbitrary model tool, SQL, filesystem, or network action | Planner is deterministic; the registry accepts only registered planned names and strict schemas; permissions and validated prior-step dependencies are rechecked. There is no arbitrary SQL/network/filesystem/code tool. | Rule-based intent classification can misclassify ambiguous requests. Model provider calls themselves are external network operations governed by privacy gates. |
| Unauthorized write/action | AI Core rejects controlled-action categories and any non-`none` side effect before handler execution. No mutation tool is registered. | Confirmation, idempotency, action audit, and owner/tenant authorization must be designed separately before any action tool is added. |
| Provider exfiltration of field-sensitive data | Gemini, Groq, and OpenRouter credentials (`CROPTWIST_GEMINI_API_KEY`, `CROPTWIST_GROQ_API_KEY`, `CROPTWIST_OPENROUTER_API_KEY`) are environment-only secrets, not API inputs or outputs. Remote field data is blocked by default (`CROPTWIST_AI_ALLOW_FIELD_DATA_TO_PROVIDERS=false`); OpenRouter additionally requires `CROPTWIST_OPENROUTER_ALLOW_FIELD_DATA=true`. Provider status reads configuration only and advertises `live_connectivity_verified=false`. | When enabled, selected question/history/evidence can leave CropTwist. OpenRouter's requested free model page warns that prompts may be logged. Deployment owners must review provider terms, retention, residency, contractual policy, and allow gates deliberately. No live call or vendor approval is claimed here. |
| Public environmental/catalog egress of field location | Existing weather and geospatial acquisition paths may send coordinates or bounding boxes to public Open-Meteo, NASA CMR/STAC, Copernicus STAC, and ISRIC WCS services. A local browser smoke observed read-only requests to those services and sent a synthetic field coordinate to Open-Meteo. This is separate from LLM-provider calls, which were disabled in that smoke. | The observed public-data reads do not currently share the AI Core provider gate. Before real-field acquisition is enabled, disclose the destination and data sent, establish user-facing consent/opt-out and minimization, review provider terms/retention, and add runtime egress controls. Ordinary pytest transport guards do not enforce application runtime privacy. |
| Credential leakage | Settings use secret types; keys are not accepted by the AI request API, returned by provider status, or included in normalized provider error categories. | Protect environment, deployment secret stores, process dumps and operator access. Rotate leaked credentials through the provider. |
| Retry amplification, cost, and denial of service | Bounded question/context/evidence/tool budgets; provider timeout, connect timeout, bounded retries/backoff, concurrency semaphore, output/frame limits and per-provider circuit state; only normalized transient failures advance chain. No cross-provider switch after partial stream output. | Limits/circuits and the generic rate limiter are process-local, not distributed. Configured providers may incur cost; current Core does not provide live price estimation. Horizontal scaling requires shared operational controls. |
| Abuse or exhaustion of generic limiter | Generic sliding-window state prunes expired subjects and is capped at 10,000 active bucket/key entries; at capacity new subjects fail closed. AI Core uses authenticated user ID and returns a retry-after response. | In-process state resets on restart and is not shared across replicas. This is not a distributed quota. Public API keys use a separate PostgreSQL-backed budget/rate path; do not infer shared storage or limits from this Core limiter. |
| False citations or fabricated measurements | Evidence labels are drawn from the selected evidence pack; every factual narrative sentence requires inline citation; the conservative citation-specific numeric check matches numeric value/unit within the cited section. Missing evidence is explicit, never silently zero. Strict validation failure discards model prose for a deterministic notice. | Label membership does not prove semantic entailment or source-row-level attribution. Numeric matching does not establish qualitative truth or agronomic safety. Domain expert review and source-backed evaluation remain necessary. |
| Trace contains sensitive prompt/farm facts | Trace persists IDs, provider attempts, selected domain names, evidence fingerprint/reference IDs, tool metadata, validation codes, optional reported usage, latency/status/error. It omits raw question, answer, full evidence values, and provider secrets. | Transcripts intentionally persist raw question/answer for conversation functionality; feedback may persist consented corrections/comments/outcomes. IDs and source IDs are sensitive metadata. Restrict database/operator access and apply retention/deletion. |
| Knowledge rights or cross-tenant leakage | Ingestion is manager-authorized and requires explicit rights confirmation plus source/publisher/version/license/restrictions. Documents/chunks carry organization scope; retrieval requires matching organization, provider/model, dimension and freshness, with a bounded candidate scan. No default corpus or embedding provider is configured. | Attestation is not independent rights verification. Embedding and search are gated separately because document text and query text may leave the service. No claim of RAG availability, true citation, or legal clearance. |
| Fake embeddings or citations | Embeddings must come from an explicitly registered adapter, pass vector validation, and match indexed provider/model/dimension/freshness. No lexical substitute is described as semantic search. Knowledge is not wired into answer synthesis. | A future adapter must preserve rights/tenant/freshness constraints and citations to specific persisted chunks. Do not enable until tests and data-policy review pass. |
| Feedback used as truth/training without consent | Feedback requires `quality_review_consent: true`, captures consent version/time, scopes rows to submitting user and trace, supports owner-only lifecycle transitions and deletion, and labels outcomes `unverified_user_reported`. There is no automatic training path. | Consent and lifecycle records are sensitive. User-reported improvement/worsening is not verified outcome evidence; any future evaluation/training use needs a separately reviewed purpose and policy. |
| Silent or indefinite retention | Existing scheduler includes `ai.retention` every 900 seconds. Bounded batches remove expired feedback (default 365 days), traces (90 days), and inactive conversations (365 days; zero disables conversation expiry/deletion). | Scheduler is process-local and only runs when app scheduler configuration enables it. Verify operational status, deployed settings, backups, deletion/cascade behavior, and user-facing retention policy. Expiry and deletion are distinct controls. |

## Provider and streaming boundaries

Default chain: Gemini `gemini-3.6-flash` → Groq `openai/gpt-oss-120b` → OpenRouter `nvidia/nemotron-3.5-super-vl:free`. The chain is configurable, but the exact configured IDs are not client-controlled. Only transient retryable failures advance; credential, permission, billing, invalid-request/schema, safety, policy, and cancellation conditions do not. OpenRouter internal endpoint routing is separate from CropTwist's application chain.

The provider adapters support provider-side streaming interfaces, but the AI Core HTTP `/requests/stream` route completes authorization, execution, validation, persistence, and commit before response headers. It then chunks the validated answer for delivery. It is not a live first-token stream. No streamed unvalidated model content is exposed by this route.

Official provider interface and privacy references were recorded in `/home/ubuntu/ai-completion-provider-docs.md` and include [Gemini model details](https://ai.google.dev/gemini-api/docs/models/gemini-3.6-flash), [Gemini generation/streaming](https://ai.google.dev/gemini-api/docs/generate-content/text-generation), [Groq API](https://console.groq.com/docs/api-reference), and the [OpenRouter free model page](https://openrouter.ai/models/nvidia/nemotron-3.5-super-vl:free). The reference was verified as documentation research, not by credentials or live inference.

## Safe logging, trace, and consent policy

Never log or add to metrics labels: question, model answer, full evidence pack, farm name/boundary, prompt body, source document text, embedding input, bridge/provider key, or authorization token. The trace may include correlation IDs, user/org/field/session IDs, intent, provider/model, provider attempt status/latency/normalized error, prompt version, selected domain names, evidence fingerprint/source identifiers, tool step metadata, validation codes, optional actual token usage, latency/status, and safe normalized error category. Trace access is restricted; it is not a content replay mechanism.

Feedback is separate from execution traces and stores content only after affirmative quality-review consent. Consent does not make user-outcome data verified, public, or automatically trainable.

## Migration and release gates

1. The checkout has one linear Alembic chain through `0028_api_key_rate_windows` (`0024` AI Core, `0025` feedback/knowledge, `0026` job ownership, `0027` invoice/payment identity, `0028` API-key rate windows). It was upgraded, downgraded, re-upgraded, and metadata-checked on a local disposable PostGIS database. Verify the target deployment revision independently; local migration success does not prove deployment state.
2. Run integration/full suites only against a designated disposable PostGIS database; repository fixtures may migrate and truncate the configured test database.
3. Validate same-organization cross-user conversation privacy, field authorization, malformed/extra-body rejection, 429 behavior, tool side-effect refusal, provider fallback/policy refusal, citations/numeric guard, feedback consent/owner scope, knowledge tenant filtering, and retention cleanup.
4. The mocked provider-adapter suite passed 73 tests locally. No live provider inference, vendor account, SMTP delivery, payment settlement, or production database was tested. The linked integration engineering report contains the full suite results and exact remaining gates.
5. Before enabling external field data, review the exact provider/model terms and set the global and OpenRouter-specific gates deliberately; confirm secret-manager handling and incident response.
6. Before multi-replica production, replace or coordinate process-local controls as appropriate, monitor scheduler execution, configure retention and deletion policies, and complete security/privacy review.
7. Do not expose prescription, yield/forecast, suitability, risk ranking, scenario, report actions, or platform mutations as operational until domain owners, validation evidence, permissions, and explicit release approval exist.
