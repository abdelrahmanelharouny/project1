# 2. EXECUTION PHILOSOPHY

Apply the following principles throughout the work.

## 2.1 Evidence over assumptions

Every scientific claim, formula, crop property, and decision rule must have identifiable evidence.

Distinguish:

- Direct field measurement.
- Laboratory measurement.
- Farmer-reported information.
- Satellite-derived estimate.
- Climate reanalysis.
- Statistical model prediction.
- Published reference value.
- Expert-validated local rule.
- Synthetic testing data.

These evidence types must never be silently treated as interchangeable.

## 2.2 Scientific accuracy over apparent completeness

A missing value is preferable to a fabricated agricultural recommendation.

A system that correctly reports insufficient evidence is better than a system that always produces a confident-looking answer.

## 2.3 Reproducibility

Every feature calculation, candidate assessment, optimization run, and comparison must be reproducible using:

- Input data snapshot.
- Data source and product versions.
- Knowledge pack version.
- Feature specification version.
- Algorithm version.
- Configuration.
- Relevant calculation assumptions.

## 2.4 Global architecture, locally validated decisions

Global software support does not imply universal agronomic validity.

Every regional recommendation must be supported by locally applicable crop knowledge, calendars, environmental evidence, and relevant constraints.

## 2.5 Implementation discipline

Inspect first, document findings, define corrections, then implement incrementally.

Preserve existing APIs and data wherever possible.

Introduce additive migrations and explicit version changes for scientific or algorithmic changes.

Do not silently change the meaning of existing features or scores.

# 4. PHASE B — ENVIRONMENTAL DATA SCIENCE AUDIT

## 4.1 Open-Meteo / ERA5 / ERA5-Land

- Units and conversion formulas.

- Time-zone behavior.
- Reanalysis limitations.
- Historical data coverage.
- Missing-value semantics.
- Source attribution.
- Product-version provenance.

Explicitly distinguish ERA5 from ERA5-Land.

Do not treat reanalysis as direct local station measurement.

Investigate whether environmental data used in different features are derived from related upstream sources, and document dependencies.

Verify that source selection prevents accidental mixing of incompatible products in one feature calculation.

## 4.2 CHIRPS v3

Audit:

- Preliminary versus final products.
- Pentad, daily, dekad, monthly, and annual products.
- Temporal accumulation semantics.
- Date boundaries.
- Variable-length end-of-month pentads.
- Missing and NoData values.
- Spatial support.
- Polygon masking.
- Small-field extraction.
- Native-resolution limitations.
- Product lineage.

A particularly important issue:

CHIRPS v3 daily products may be derived by distributing pentad rainfall totals using ERA5-based or IMERG-based daily information.

Document the dependency structure.

Do not treat CHIRPS RNL and ERA5 as fully independent evidence when comparing their daily temporal patterns.

Do not double-count overlapping precipitation products.

Validate pentad-to-month and pentad-to-season aggregation independently.

## 4.3 SoilGrids

Review:

- Actual WCS request and response structure.
- Coverage identifiers.
- Variable encoding.
- Units.
- Depth intervals.
- Quantile interpretation.
- Mean versus median.
- Spatial masking.
- Partial-pixel inclusion.
- Sub-grid fallback.
- NoData handling.
- Field-level representativeness.

Distinguish:

- Soil property concentration.
- Soil property stock.
- Volumetric measurements.
- Gravimetric measurements.
- Prediction uncertainty.
- Measurement uncertainty.

Specifically verify Soil Organic Carbon:

A concentration value in g/kg is not an organic-carbon stock in t/ha.

Calculating stocks may require soil depth, bulk density, coarse fragments, and appropriate spatial assumptions.

Do not derive a root-zone profile from a single 0–5 cm layer.

### Spatial aggregation requirements

Investigate whether the current field extraction method should support fractional pixel-area weighting instead of relying exclusively on all-touched or center-based inclusion.

Preserve the native resolution of every input.

If a field is smaller than a source grid cell, explicitly document that the extracted value may represent the surrounding grid cell rather than a true field-specific measurement.

For SoilGrids prediction quantiles, investigate appropriate uncertainty propagation when aggregating several pixels to a field.

Do not simply average per-pixel lower and upper quantiles and automatically label the results as a formal 90% field-level prediction interval.

- Missing objectives.

Use a suitable multi-objective strategy, such as repeated epsilon-constraint optimization where appropriate.

Do not claim that a single solver status proves that an entire Pareto frontier is optimal.

# 10. PHASE H — SCIENTIFIC BENCHMARKING AND TESTING

The existing 314-test history is a baseline, not a substitute for independent scientific validation.

Build a Scientific Benchmark Suite.

## 10.1 Golden numerical tests

For each important formula:

- Define a documented reference case.
- Calculate an independently verified expected result.
- Compare implementation output.
- Test unit conversions.
- Test boundary conditions.
- Test numerical tolerances.
- Explain the source of the expected result.

Where possible, use official worked examples or independently implemented reference calculations.

## 10.2 Property-based tests

Test mathematical properties, not only fixed examples.

Examples:

- Increasing effective rainfall under unchanged assumptions must not increase net irrigation demand.
- Increasing available water allocation must not make a previously feasible strategy infeasible solely because of that change.
- Invalid hard constraints must never be silently relaxed.
- A dominated strategy must never appear as non-dominated.
- Unit conversions must preserve physical quantities.
- Identical input snapshots and configurations should reproduce identical deterministic outputs.

These properties must be qualified by the assumptions of the underlying calculation.

## 10.3 Metamorphic testing

Test system behavior when:

- Units change but physical quantities remain equivalent.
- Polygon coordinates are transformed into another valid CRS.
- Records are reordered.
- Irrelevant observations are added.
- Missing intervals are introduced.
- Data products are switched.
- Knowledge pack versions change.
- Optimization weights change.

## 10.4 Cross-component integration

Validate that:

- Provenance survives every processing stage.
- Feature snapshots reference correct observations.
- Knowledge versions are attached to evaluations.
- Optimization runs preserve the correct feature snapshots.
- Frontend labels match backend meanings.
- Synthetic data never masquerades as measured evidence.
- Tenant isolation remains enforced.

## 10.5 Performance and operational validation

Review:

- Large field datasets.
- Many years of observations.
- Raster extraction memory usage.
- Background job reliability.
- Database query patterns.
- Spatial index usage.
- API pagination.
- Retry behavior.
- Provider health degradation.
- Long-running optimization jobs.

Do not introduce unnecessary infrastructure or distributed services without a demonstrated need.

# 14. FINDING CLASSIFICATION

Every finding must include:

- Finding ID.
- Severity.
- Affected component.
- Existing behavior.
- Expected scientific or technical behavior.
- Evidence/reference.
- Reproducible example.
- Impact.
- Recommended correction.
- Required regression tests.
- Implementation status.

Use these severity levels:

**Critical:** Can produce materially incorrect results, misleading recommendations, invalid constraints, data leakage, or incorrect physical quantities.

**High:** Weakens scientific validity, reproducibility, core decision logic, or global applicability.

**Medium:** Reduces reliability, interpretability, completeness, maintainability, or performance.

**Low:** Documentation, usability, or non-blocking improvement.

- Original finding.

- Relevant files.
- Added tests.

- Scientific reference.
- Remaining limitation.
- Final status.
