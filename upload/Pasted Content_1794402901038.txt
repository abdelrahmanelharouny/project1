# 2. GLOBAL ENGINEERING RULES

These rules apply to every workstream.

## Evidence integrity

Every observation must retain:

- Source/provider.
- Acquisition timestamp.
- Observation or forecast period.
- Spatial resolution.
- Units.
- Geographic coverage.
- Processing method.
- Quality flags.
- Missing-data status.
- Provenance.
- Whether the value is observed, derived, forecast, projected, estimated, or synthetic.

Never mix observed, forecast, projected, and synthetic data without explicit classification.

Synthetic data must never be represented as real satellite or climate observations.

## Scientific integrity

- Use established scientific methods and documented formulas.
- Preserve original measurements.
- Record assumptions and uncertainty.
- Never invent missing observations.
- Do not infer field-level precision beyond source resolution.
- Distinguish correlation from causation.
- Never claim a model is scientifically validated without independent validation.
- Make unsupported outputs unavailable rather than presenting false precision.

## Architecture

Preserve:

Data Providers → Normalization → Evidence Store → Feature Engine → Agronomic Engines → Scenario Intelligence → Recommendation Registry → Presentation → Feedback.

Every recommendation must continue flowing through the centralized registry.

## Database safety

- All migrations must be additive and carefully reversible where appropriate.
- Preserve existing farm, field, observation, recommendation, scenario, and feedback data.
- Never reset the active database.
- Never drop production tables.
- Do not perform destructive migrations.
- Test migrations on isolated databases.
- Verify migration upgrade and downgrade behavior.
- Preserve tenant isolation.

## Implementation quality

- Reuse existing services and schemas.
- Avoid duplicate providers.
- Avoid unnecessary dependencies.
- Avoid monolithic modules.
- Maintain strict typing.
- Add meaningful tests.
- Preserve API compatibility where possible.
- Update English and Arabic translations.
- Keep the UI consistent with the existing design system.

# 3. WORKSTREAM A — P2.1 SATELLITE INTELLIGENCE

Priority: Critical

## Objective

Introduce reliable vegetation intelligence that allows CropTwist to understand crop condition and vegetation changes over time.

The platform should be able to identify vegetation patterns, stress signals, seasonal changes, and spatial variability while respecting the limitations of satellite observations.

## A. Data Provider Architecture

Inspect existing Earth observation providers before implementation.

Support suitable sources such as:

- Sentinel-2.
- Landsat 8/9.
- MODIS, where temporal resolution is more useful than spatial resolution.
- Other compatible public Earth observation products where justified.

Prefer authoritative provider APIs and documented data products.

Potential access methods include:

- Copernicus Data Space Ecosystem.
- Microsoft Planetary Computer.
- Google Earth Engine, only when its authentication and deployment requirements are explicitly configured.
- Other documented public APIs or STAC-compatible sources.

Do not introduce multiple providers that produce redundant data without a clear advantage.

Build a reusable provider interface supporting:

- Search by field geometry.
- Date-range queries.
- Cloud coverage filtering.
- Product metadata.
- Spatial resolution metadata.
- Acquisition timestamps.
- Asset retrieval.
- Provider-specific error handling.
- Rate limiting.
- Retry policies.
- Caching.
- Provenance.

## B. Vegetation Indices

Implement scientifically correct calculations for:

### NDVI

\[
NDVI = \frac{NIR-Red}{NIR+Red}
\]

### EVI

\[
EVI = G\frac{NIR-Red}{NIR+C_1 Red-C_2 Blue+L}
\]

Use documented coefficients for the selected sensor/product.

Also evaluate whether additional indices are useful:

- SAVI.
- NDMI.
- NDWI.
- NBR where relevant.

Do not implement indices without the necessary spectral bands.

Handle:

- NoData.
- Cloud contamination.
- Shadow contamination.
- Invalid pixels.
- Division by zero.
- Sensor-specific band mappings.
- Reflectance scaling.
- Geospatial reprojection.

Preserve the original raster metadata.

## C. Temporal Vegetation Intelligence

Build time-series capabilities:

- Field-level NDVI/EVI statistics.
- Monthly and seasonal summaries.
- Vegetation trajectories.
- Historical baselines.
- Anomaly detection.
- Trend detection.
- Spatial distribution summaries.
- Missing-observation awareness.

Use seasonal baselines rather than naive comparisons across different months.

Distinguish:

- Genuine vegetation decline.
- Seasonal dormancy.
- Harvest-related changes.
- Cloud-related gaps.
- Insufficient observation history.

Never classify low NDVI alone as a crop disease.

## D. Field-Level Spatial Intelligence

Support:

- Field boundary masking.
- Pixel-level validity masks.
- Field-level zonal statistics.
- Percentile distributions.
- Spatial variability summaries.
- Sub-field zone identification where resolution supports it.

Respect the source resolution.

A 10-meter satellite product cannot justify arbitrary centimeter-level field predictions.

Avoid false precision for small fields.

## E. Vegetation Stress Intelligence

Build evidence-based vegetation stress signals.

Combine vegetation indices with relevant environmental context where available:

- Temperature.
- Rainfall.
- Soil moisture.
- Water availability.
- Evapotranspiration.
- Crop growth stage.
- Planting and harvest dates.

Distinguish observed vegetation change from inferred possible causes.

Do not claim drought, disease, nutrient deficiency, or irrigation failure from NDVI alone.

## F. Frontend

Add or extend Satellite Intelligence within CropTwist.

Provide:

- Field map overlays.
- NDVI/EVI time series.
- Observation dates.
- Cloud-quality indicators.
- Source and resolution details.
- Historical comparisons.
- Spatial variability visualization.
- Missing-data explanations.

Arabic and English support is mandatory.

# 6. WORKSTREAM D — P2.4 ROTATION FAILURE LAB

Priority: Critical

## Objective

Introduce a rigorous scenario stress-testing system that evaluates how crop rotations behave under adverse conditions.

The system should answer:

"What could make this rotation fail, how severe could the impact be, and which alternative is more resilient?"

This is not a simple what-if calculator.

## A. Scenario Engine

Inspect existing scenario, digital twin, robustness, and sensitivity modules.

Extend rather than duplicate them.

Support configurable stress scenarios:

- Severe drought.
- Heatwave.
- Delayed planting.
- Heavy rainfall.
- Water restrictions.
- Nutrient price increases.
- Fertilizer availability constraints.
- Labor shortages.
- Equipment constraints.
- Market-price shocks.
- Combined climate and operational stress.

Each scenario must have explicit parameters, provenance, and assumptions.

## B. Rotation Stress Testing

Evaluate multiple candidate rotations under the same conditions.

Compare:

- Water demand.
- Water availability.
- Nutrient balance.
- Soil organic carbon trajectory.
- Erosion risk.
- Crop timing.
- Operational feasibility.
- Yield estimates only when a validated yield model exists.
- Economic outcomes only when adequate market and cost evidence exists.

Do not invent yields or profits.

If a variable cannot be estimated reliably, label it unavailable.

## C. Robustness Metrics

Implement scientifically and mathematically defined metrics:

- Worst-case outcome.
- Mean scenario outcome.
- Scenario variance.
- Downside risk.
- Feasibility rate.
- Constraint violation frequency.
- Sensitivity to parameter changes.
- Regret relative to the best alternative in each scenario.

Define all formulas and units.

Do not combine unrelated metrics into an arbitrary overall score.

## D. Scenario Comparison

Compare at least:

- Existing rotation.
- Recommended rotation.
- Alternative resilient rotation.

Use the same baseline assumptions.

Explain why each alternative performs differently.

## E. Failure Explanation

Every detected failure must explain:

- What failed.
- Which constraint was violated.
- Which evidence supports the conclusion.
- Under which scenario.
- Severity.
- Whether it is certain, estimated, or conditional.
- Potential mitigation.

## F. Frontend

Build an interactive Rotation Failure Lab.

Support:

- Scenario selection.
- Parameter adjustment.
- Rotation comparison.
- Risk breakdown.
- Robustness visualization.
- Constraint violations.
- Evidence-linked explanations.
- Scenario reproducibility.

# 7. WORKSTREAM E — P2.5 ADAPTIVE EVIDENCE ACQUISITION

Priority: Critical

## Objective

Make CropTwist capable of identifying missing information that could materially change an agricultural decision.

Instead of simply saying "data unavailable", it should explain what information is missing, why it matters, and what the farmer can do to obtain it.

This is a major product differentiator.

## A. Evidence Gap Detection

Inspect all existing evidence packs and feature requirements.

Build a structured evidence-gap model.

Potential gaps include:

- Missing soil samples.
- Stale weather observations.
- Insufficient satellite coverage.
- Missing planting dates.
- Missing crop history.
- Missing irrigation records.
- Missing fertilizer application history.
- Missing field geometry.
- Missing operational constraints.
- Missing market information.

Each gap must include:

- Affected decision.
- Required evidence.
- Current evidence status.
- Importance.
- Freshness requirement.
- Spatial relevance.
- Potential impact.

## B. Value of Information

Implement a decision-aware Value of Information framework.

Estimate whether obtaining a missing piece of evidence could change the recommended decision.

Use available scenario and sensitivity infrastructure.

The framework should consider:

- Current candidate decisions.
- Uncertainty.
- Sensitivity to missing variables.
- Expected change in decision ranking.
- Cost and effort of collecting evidence.
- Time sensitivity.

Do not assign fake monetary values to information.

If collection cost is unknown, use qualitative cost categories.

## C. Evidence Acquisition Plans

Generate actionable acquisition suggestions:

- Collect a soil sample.
- Record the planting date.
- Upload historical irrigation records.
- Obtain a new satellite observation.
- Verify field boundaries.
- Record fertilizer applications.
- Confirm available water.
- Provide machinery or labor constraints.

Each suggestion must explain:

1. What is missing.
2. Why it matters.
3. Which decision it affects.
4. How to obtain it.
5. Whether it is urgent.
6. What uncertainty it could reduce.

## D. Decision Recalculation

When new evidence is submitted:

- Validate it.
- Preserve provenance.
- Update the relevant evidence pack.
- Recalculate affected engines.
- Reevaluate recommendations.
- Preserve previous versions.
- Record which decision changed and why.

Do not regenerate the entire system unnecessarily when only one evidence domain changed.

## E. Frontend

Add an Adaptive Evidence panel.

Show:

- Evidence completeness.
- Critical missing inputs.
- Suggested data collection actions.
- Decision sensitivity.
- Evidence acquisition history.
- Recommendations affected by newly submitted evidence.
