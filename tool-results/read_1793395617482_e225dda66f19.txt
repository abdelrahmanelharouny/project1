    34→# PART I — EXECUTION PROMPT FOR THE CODING AGENT
    35→
    36→## 1. Your Role
    37→
    38→You are acting as a principal software architect, senior Python backend engineer, geospatial data engineer, agricultural decision-support engineer, optimization engineer, frontend architect, QA engineer, and technical writer working as one disciplined engineering team.
    39→
    40→Your task is to implement **FieldShift**, a maintainable, testable, explainable, global-capable agricultural decision-support platform. You are not being asked to create a mock landing page, a static dashboard, a notebook-only prototype, or a collection of disconnected API calls. You must build a coherent software product with clear domain boundaries, reproducible analytical pipelines, traceable data, robust APIs, a useful farmer experience, and automated tests.
    41→
    42→You must work directly in the repository available in your environment. Before changing anything, inspect the existing repository, identify its current state, and preserve useful existing work. Do not assume that the repository is empty.
    43→
    44→## 2. Mission
    45→
    46→Build a system that helps farmers and agricultural advisors explore, compare, and improve crop-rotation strategies by combining:
    47→
    48→1. Environmental and climate information.
    49→2. Soil measurements and soil-property estimates.
    50→3. Crop characteristics and regional agronomic knowledge.
    51→4. Farm history and management practices.
    52→5. Farmer priorities, resource limits, market access, and equipment constraints.
    53→6. Explainable optimization and scenario simulation.
    54→
    55→The product must help users understand not only **which rotation alternatives are possible**, but also:
    56→
    57→- why each alternative was generated;
    58→- which hard constraints it satisfies or violates;
    59→- what data and agronomic knowledge support it;
    60→- what the trade-offs are between water, soil, economic return, resilience, and operational feasibility;
    61→- what information is missing;
    62→- where uncertainty is high;
    63→- what must be reviewed by a local agronomist or the farmer before acting.
    64→
    65→FieldShift is a **decision-support system**, not an autonomous agronomist and not a guarantee of yield, water savings, soil improvement, or profit.
    66→
    67→## 3. Non-Negotiable Execution Rules
    68→
    69→Follow these rules throughout implementation:
    70→
    71→1. **Inspect before modifying.** Start with `pwd`, repository tree, git status, existing README, dependency manifests, tests, and current application entry points. Do not overwrite or delete existing work without understanding it.
    72→2. **Implement in vertical slices.** Deliver a working end-to-end path early, then expand it. Do not create dozens of empty files and claim completion.
    73→3. **Do not stop at architecture documents.** Documentation is required, but you must implement and test actual application code.
    74→4. **Do not implement the entire product in one uncontrolled code dump.** Follow the milestones in this document. Finish one milestone with tests and a concise report before moving to the next.
    75→5. **Use currently supported stable dependency versions.** Verify the current official documentation when selecting versions. Pin exact resolved versions in lock files. Do not invent package versions.
    76→6. **Never fabricate scientific data, crop traits, crop calendars, crop coefficients, disease rules, or model accuracy.** Unknown values must remain unknown and carry a missing-data reason.
    77→7. **Synthetic data must always be visibly labelled.** It must never be mixed with observed or externally sourced data without explicit provenance fields.
    78→8. **NASA is future-only.** Do not block the project on NASA Earthdata credentials, NASA APIs, NASA data downloads, or NASA connectors. Create clean extension points so future NASA providers can be added without changing business logic. Do not spend the first implementation phase writing inactive NASA connector stubs beyond documented interfaces and adapter registration tests.
    79→9. **Do not confuse data resolution with field-level truth.** Never upsample coarse raster data and claim that the resulting pixels have gained real spatial detail.
    80→10. **Preserve source metadata.** Every environmental observation and derived feature must be traceable to its product, version, time range, spatial support, processing version, and quality state.
    81→11. **Do not silently impute missing agricultural values.** If an input required for a calculation is missing, return a structured incomplete/not-evaluated result. Any optional imputation must be explicit, configurable, documented, and represented in provenance.
    82→12. **Separate hard constraints from soft objectives.** A high weighted score must never compensate for violating a hard agronomic, legal, market, calendar, equipment, or water constraint.
    83→13. **Do not claim an optimization solution is globally optimal unless the solver proves `OPTIMAL`.** Distinguish `OPTIMAL`, `FEASIBLE`, `INFEASIBLE`, `UNKNOWN`, timeout, and partial result states.
    84→14. **Use deterministic tests.** Seed random generators and make synthetic scenario generation reproducible.
    85→15. **Validate all geometry and units.** Invalid geometries, unsupported units, invalid time windows, and malformed source payloads must produce actionable errors.
    86→16. **Keep business logic out of HTTP route handlers and UI components.** Use application services and domain modules.
    87→17. **Protect tenant data.** Every farm/field query must be authorized against the requesting user’s organization or explicit membership.
    88→18. **Add tests with every meaningful feature.** Do not postpone all testing until the end.
    89→19. **Update documentation when behavior changes.** Keep API examples, schemas, architecture decisions, and setup instructions consistent with the implementation.
    90→20. **Be honest in reports.** State what works, what is mocked, what is incomplete, and what has not been validated.
    91→
    92→If you find a conflict between this prompt and the current repository, inspect the code and document the conflict before deciding. Prefer small, reversible changes.

   128→# PART II — PRODUCT DEFINITION
   129→
   130→## 5. Product Name and Positioning
   131→
   132→**Name:** FieldShift  
   133→**Descriptor:** Adaptive Farm Intelligence & Crop-Rotation Decision Support  
   134→**Product category:** Agricultural decision-support platform  
   135→**Primary users:** Farmers, farm managers, agronomists, agricultural cooperatives, and agricultural research/advisory teams.
   136→
   137→### Product statement
   138→
   139→FieldShift helps farmers design, compare, stress-test, and learn from crop-rotation strategies using environmental observations, soil information, crop knowledge, farm records, and farmer-defined objectives. It provides transparent evidence and trade-offs while preserving farmer and agronomist authority over final decisions.
   140→
   141→## 6. Target Users and Their Needs
   142→
   143→### 6.1 Farmer
   144→
   145→Needs:
   146→- a simple explanation of field conditions;
   147→- practical rotation alternatives;
   148→- visibility into water and operational constraints;
   149→- a clear seasonal action calendar;
   150→- offline recording when connectivity is poor;
   151→- a way to record actual activities and outcomes;
   152→- control over which personal and farm data are shared.
   153→
   154→The farmer should not need to understand NDVI, ET0, raster resolution, or optimization mathematics to use the main workflow.
   155→
   156→### 6.2 Agronomist / Agricultural Advisor
   157→
   158→Needs:
   159→- source-level evidence and assumptions;
   160→- crop and soil parameter inspection;
   161→- rule review and override capabilities with audit history;
   162→- missing-data and uncertainty diagnostics;
   163→- comparison of alternative rotations;
   164→- a way to add locally validated knowledge.
   165→
   166→### 6.3 Farm Manager / Cooperative Manager
   167→
   168→Needs:
   169→- multiple fields and farms;
   170→- resource and water allocation views;
   171→- operational calendars;
   172→- aggregated summaries with permissions;
   173→- exportable reports.
   174→
   175→### 6.4 Research / Platform Administrator
   176→
   177→Needs:
   178→- provider health and ingestion status;
   179→- dataset and knowledge version management;
   180→- quality and coverage monitoring;
   181→- controlled access to aggregate, privacy-protected data;
   182→- algorithm versioning and reproducibility.
   183→
   184→## 7. Primary User Journey
   185→
   186→The principal journey must work end to end:
   187→
   188→1. User registers and creates or joins an organization.
   189→2. User creates a farm and selects country, administrative region, timezone, currency, preferred language, and unit system.
   190→3. User creates a field by drawing a polygon, importing GeoJSON, or entering a supported geospatial file.
   191→4. System validates geometry, calculates area using an appropriate geodesic/projected method, and stores a versioned boundary.
   192→5. User enters soil test values or imports a soil report.
   193→6. User selects current/previous crops and records management practices.
   194→7. System obtains available environmental data from configured alternative providers or accepts user-uploaded data.
   195→8. System creates a field data-readiness report that shows what is available, its coverage, age, resolution, and quality.
   196→9. System computes only the environmental/agronomic features for which the required inputs exist.
   197→10. User configures priorities and hard constraints.
   198→11. System creates a baseline representing the existing rotation and candidate rotation alternatives.
   199→12. User compares alternatives by water, soil, operational, economic, and resilience criteria.
   200→13. User runs climate/water stress scenarios.
   201→14. User saves a plan and receives a season-oriented checklist.
   202→15. During the season, user records actual operations, observations, and issues.
   203→16. After harvest, user records yield, costs, water use, and feedback.
   204→17. System compares expected versus observed outcomes and makes future estimates more locally informed, without silently rewriting historical decisions.
   205→
   206→## 8. Scope and Non-Goals
   207→
   208→### In scope
   209→
   210→- Global-capable farm and field management.
   211→- Geospatial field boundaries and environmental data extraction.
   212→- Replaceable data providers.
   213→- Alternative environmental datasets and user-uploaded files.
   214→- Soil and crop knowledge catalogs.
   215→- Crop history and farm management records.
   216→- Data quality, lineage, uncertainty, and coverage reporting.
   217→- Water budgeting.
   218→- Soil-health indicator tracking.
   219→- Crop rotation candidate generation and constrained optimization.
   220→- Scenario analysis and stress testing.
   221→- Pest/disease rotation warnings based on validated rules.
   222→- Bare-soil-window and cover-crop planning.
   223→- Explainable strategy comparison.
   224→- Farmer journal, seasonal planning, offline capture, and synchronization.
   225→- Agronomist review and approval workflow.
   226→- Multi-language/unit support.
   227→
   228→### Explicit non-goals for the initial release
   229→
   230→- Autonomous crop disease diagnosis from a phone photo.
   231→- Automated irrigation-valve control.
   232→- Guaranteed yield or profit prediction.
   233→- Guaranteed soil carbon sequestration estimates.
   234→- Legal or subsidy advice.
   235→- Fully validated crop recommendations for every country and crop.
   236→- A general-purpose conversational AI that invents agronomic facts.
   237→- Mandatory NASA integration.
   238→- Training a new deep-learning model before a specific data-backed need exists.

   242→# PART III — TECHNICAL ARCHITECTURE
   243→
   244→## 9. Architecture Decision: Modular Monolith
   245→
   246→Implement a **modular monolith** first. The modules must have clear boundaries, independent tests, and explicit contracts. Do not introduce microservices in the initial release.
   247→
   248→Recommended top-level layers:
   249→
   250→1. Presentation layer: React web/PWA.
   251→2. API layer: FastAPI routes, authentication, authorization, request/response schemas.
   252→3. Application layer: use cases and orchestration.
   253→4. Domain layer: farms, crops, soil, water, rotations, scenarios, journal, knowledge.
   254→5. Intelligence layer: feature calculations, optimization, simulation, explainability.
   255→6. Data platform layer: provider adapters, ingestion, validation, normalization, provenance.
   256→7. Infrastructure layer: PostgreSQL/PostGIS, object storage, Redis, background workers, logging.
   257→
   258→### Dependency direction
   259→
   260→- Presentation calls API contracts only.
   261→- API calls application services.
   262→- Application services coordinate domain services and repositories.
   263→- Domain and intelligence modules must not import FastAPI request/response objects.
   264→- Provider adapters must map external payloads into canonical DTOs; they must not return ORM entities.
   265→- Repositories own persistence details.
   266→- External provider SDKs must not leak into the domain layer.
   267→
   268→### Asynchronous work
   269→
   270→Use background jobs for large raster downloads, spatial extraction, long feature runs, optimization jobs, Monte Carlo simulations, report generation, and bulk imports.
   271→
   272→The API should return `202 Accepted` plus a job identifier for work that should not block an HTTP request. Job state must be persisted in the database; Redis is a queue/cache, not the source of truth for job history.
   273→

   277→
   278→### Backend

   280→- FastAPI.
   281→- Pydantic v2.

   290→- Google OR-Tools CP-SAT for constrained rotation optimization.
   291→- Pytest for backend tests.
   292→
   293→### Frontend

   295→- Vite unless the existing application uses another suitable framework.
   296→- Tailwind CSS or the existing design system.

   313→### Version discipline

   319→# PART IV — DATA PLATFORM
   320→
   321→## 11. Data Source Strategy
   322→
   323→The initial product must run without NASA. Implement alternative providers and imports now, while keeping the canonical data model provider-independent.
   324→
   325→### 11.1 Initial providers and source types
   326→
   327→#### A. Open-Meteo Historical Weather API
   328→
   329→Use for suitable historical climate variables such as air temperature, precipitation where provided by the selected model, humidity, wind, radiation, ET0 where supported, and soil variables only when the selected model/product exposes them.
   330→
   331→Implementation requirements:
   332→- Explicitly select the model/product rather than relying blindly on a changing default.
   333→- For multi-decadal climate trend analysis, prefer a consistent reanalysis product such as ERA5 or ERA5-Land over a seamlessly changing best-match series.
   334→- Store model name, product/version, spatial resolution, temporal resolution, retrieval time, timezone basis, and variable metadata.
   335→- Respect the provider's allowed request sizes, caching guidance, rate limits, attribution, and terms.
   336→- Treat reanalysis as model-based gridded data, not a direct field sensor observation.
   337→
   338→Official documentation: https://open-meteo.com/en/docs/historical-weather-api
   339→
   340→#### B. CHIRPS v3
   341→
   342→Use as an alternative quasi-global rainfall dataset. It is land-focused and spans approximately 60 degrees north to 60 degrees south, with near-global longitude coverage and a 0.05-degree grid. The provider publishes preliminary and final products. Select and record which product was used.
   343→
   344→Implementation requirements:
   345→- Prefer pentadal/monthly/annual products for climate summaries where appropriate.
   346→- Use daily products carefully; do not use downscaled daily fields as unquestioned evidence for daily rainfall extremes.
   347→- Do not claim global coverage outside its documented latitude/land coverage.
   348→- Preserve native raster resolution and nodata masks.
   349→- Record product version and preliminary/final status.
   350→- Provide a bulk/file ingestion workflow and a spatial-subset extraction workflow.
   351→
   352→Official sources:
   353→- https://www.chc.ucsb.edu/data/chirps3
   354→- https://www.chc.ucsb.edu/data
   355→
   356→#### C. SoilGrids
   357→
   358→Use as an optional gridded soil-property source, never as a replacement for field laboratory analysis. It offers global soil-property predictions and uncertainty information, but the REST API may be unavailable or unstable.
   359→
   360→Implementation requirements:
   361→- Do not depend on the SoilGrids REST API for core application availability.
   362→- Prefer documented WCS spatial subsets or WebDAV-hosted data where operationally suitable.
   363→- Record property, depth interval, quantile, units, prediction interval, source version, and spatial support.
   364→- Treat values as model predictions with uncertainty, not measured field samples.
   365→- Expose a provider-health state and graceful degradation.
   366→
   367→Official sources:
   368→- https://docs.isric.org/globaldata/soilgrids/
   369→- https://docs.isric.org/globaldata/soilgrids/wcs.html
   370→- https://docs.isric.org/globaldata/soilgrids/WebDav.html
   371→
   372→#### D. FAO GAEZ
   373→
   374→Use crop suitability and agroecological context as broad screening information. GAEZ is not field-level ground truth. Its regular grid is coarse relative to many farms.
   375→
   376→Implementation requirements:
   377→- Import only the modules/products needed for supported workflows.
   378→- Record baseline, climate scenario, management level, irrigation/rainfed context, crop, and product version.
   379→- Show the product's spatial support and limitations.
   380→- Never translate suitability classes directly into a guaranteed crop recommendation.
   381→
   382→Official source: https://www.fao.org/gaez/gaezv4/en
   383→
   384→#### E. FAO Crop Calendar
   385→
   386→Use as a reference for planting and harvesting windows where applicable. Do not assume an official public API exists. Build a curated import mechanism with region, crop, season, source, effective dates, and validation status.
   387→
   388→Official portal: https://cropcalendar.apps.fao.org/
   389→
   390→#### F. Farmer-provided data
   391→
   392→Support structured forms and file imports for:
   393→- soil laboratory reports;
   394→- crop history;
   395→- field boundaries;
   396→- irrigation events and allocations;
   397→- yield and harvest records;
   398→- management practices;
   399→- crop calendars validated by local advisors;
   400→- equipment and market constraints.
   401→
   402→Support CSV and GeoJSON in the initial implementation. Add GeoPackage and other formats through a controlled import pipeline, not by trusting arbitrary files.
   403→
   404→#### G. Synthetic fixtures
   405→
   406→Create reproducible synthetic environments for testing. These must have `is_synthetic=true`, an explicit generator version, seed, scenario profile, and purpose. Never display synthetic measurements as real observations.
   407→
   408→### 11.2 Future NASA integration
   409→
   410→NASA is not an initial runtime dependency. Keep extension points for future products such as SMAP, GPM, Landsat, MODIS, ECOSTRESS, GRACE/GRACE-FO, NASA POWER, and elevation products. Do not implement these integrations until the project has a clear use case, access plan, product documentation review, and tests.
   411→
   412→When a NASA provider is eventually added, it must implement the same provider contracts and canonical output schemas as all other sources.
   413→
   414→## 12. Provider Abstraction
   415→
   416→Define provider interfaces around normalized domain data, not provider-specific response payloads.
   417→
   418→Suggested interfaces:
   419→
   420→```python
   421→from datetime import datetime
   422→from typing import Protocol, Sequence
   423→
   424→class EnvironmentalDataProvider(Protocol):
   425→    provider_code: str
   426→
   427→    async def fetch_observations(
   428→        self,
   429→        *,
   430→        area_of_interest: "AreaOfInterest",
   431→        variables: Sequence[str],
   432→        start: datetime,
   433→        end: datetime,
   434→        options: dict | None = None,
   435→    ) -> "ProviderFetchResult":
   436→        ...
   437→```
   438→
   439→Also define separate contracts for:
   440→- raster providers;
   441→- tabular providers;
   442→- soil-property providers;
   443→- crop-knowledge importers;
   444→- local file importers.
   445→
   446→A provider result should include:
   447→- normalized observations or asset references;
   448→- source/product identifiers;
   449→- retrieval metadata;
   450→- coverage diagnostics;
   451→- warnings;
   452→- provider request identifier;
   453→- raw payload/file reference where retention is permitted.
   454→
   455→### Provider registry
   456→
   457→Implement a registry/factory keyed by provider code. Use configuration to activate/deactivate providers. A provider outage must not crash unrelated application modules. Provider errors must be surfaced as structured job failures and data-coverage warnings.
   458→
   459→### Provider contract tests
   460→
   461→Each provider must pass the same contract suite:
   462→- returns valid canonical objects;
   463→- includes provenance;
   464→- preserves native temporal support;
   465→- includes units;
   466→- flags missing/nodata values;
   467→- rejects invalid date ranges and unsupported variables;
   468→- handles timeouts and retryable errors;
   469→- does not duplicate records on retry;
   470→- is safe to rerun idempotently where possible.
   471→
   472→## 13. Canonical Data Model
   473→
   474→Create a canonical observation/asset model independent of data provider.
   475→
   476→### 13.1 Observation fields
   477→
   478→At minimum:
   479→
   480→- `id` (UUID)
   481→- `field_id` (nullable for broader area-level records)
   482→- `variable_code`
   483→- `value` (nullable if missing/nodata)
   484→- `unit`
   485→- `observed_at` or `period_start`/`period_end`
   486→- `time_support` (instant, hourly, daily, pentadal, monthly, seasonal, etc.)
   487→- `source_id`
   488→- `dataset_product_id`
   489→- `product_version`
   490→- `spatial_support_type` (point, grid_cell, polygon_average, field_intersection, station, lab_sample)
   491→- `spatial_resolution_m` where known
   492→- `geometry` or raster/asset reference where applicable
   493→- `quality_status`
   494→- `uncertainty_value` and `uncertainty_type` where available
   495→- `is_synthetic`
   496→- `retrieved_at`
   497→- `processing_version`
   498→- `metadata` JSONB
   499→
   500→Do not force every data type into one oversized table if the implementation needs separate raster assets and observation tables. Maintain the canonical semantics.
   501→
   502→### 13.2 Source metadata
   503→
   504→Every source/product must have:
   505→- provider name;
   506→- product code;
   507→- product version;
   508→- variables;
   509→- unit conventions;
   510→- spatial/temporal resolution;
   511→- spatial/temporal coverage;
   512→- license and attribution;
   513→- documentation URL;
   514→- retrieval method;
   515→- known limitations;
   516→- active/deprecated status.
   517→
   518→### 13.3 Provenance graph
   519→
   520→Derived features must point to the exact input observation/asset snapshot and processing version. Optimization runs must point to:
   521→- feature snapshot;
   522→- crop-knowledge version;
   523→- constraint set version;
   524→- objective weights;
   525→- solver version and parameters;
   526→- scenario assumptions;
   527→- algorithm version.
   528→
   529→Historical results must remain reproducible even after new data arrives.
   530→
   531→## 14. Spatial and Temporal Harmonization
   532→
   533→### 14.1 Spatial rules
   534→
   535→- Store user field geometry in EPSG:4326 for interchange, with PostGIS geometry/geography support.
   536→- Validate polygons, rings, holes, self-intersections, coordinate order, and antimeridian edge cases where relevant.
   537→- Calculate area with geodesic or appropriate equal-area methods, not planar square degrees.
   538→- Use spatial indexes for query performance.
   539→- Preserve native input raster resolution and CRS.
   540→- For raster extraction, record resampling method and aggregation method.
   541→- Use area-weighted aggregation where appropriate; distinguish center-point sampling from polygon statistics.
   542→- Preserve nodata masks and valid-pixel coverage.
   543→- If field size is much smaller than source pixel size, show a warning that the estimate is not field-resolved.
   544→- Never create false spatial precision by upsampling a coarse grid.
   545→
   546→### 14.2 Temporal rules
   547→
   548→- Store timestamps in UTC.
   549→- Store farm timezone separately and use it for local operation calendars and UI display.
   550→- Keep original temporal support. Do not transform a monthly total into daily values without a documented disaggregation model.
   551→- Distinguish observation date, accumulation period, retrieval date, and publication date.
   552→- Support growing seasons that cross calendar years and both hemispheres.
   553→- Use crop- and region-specific growing windows; do not assume northern-hemisphere seasonality globally.
   554→- For long-term trends, use internally consistent dataset products and document any product transitions.
   555→
   556→### 14.3 Spatial-temporal resolution compatibility
   557→
   558→The pipeline must be able to align variables for analysis without pretending they have equal information content. An analytical grid/time step is a processing choice, not a claim that all inputs have that precision. Keep per-variable native support metadata and quality flags after harmonization.
   559→
   560→## 15. Unit System and Data Dictionary
   561→
   562→Use SI units internally wherever sensible. Store the original source unit and conversion metadata where needed. Use a unit library for conversions where practical.
   563→
   564→Examples:
   565→- air temperature: degrees Celsius;
   566→- precipitation depth: mm per defined period;
   567→- soil moisture: m3/m3 when volumetric;
   568→- ET0 and ETc: mm per defined period;
   569→- water volume: m3;
   570→- field area: hectares internally for agricultural summaries, with source geometry retained;
   571→- soil organic carbon: source-defined unit, normalized only after verifying depth/basis;
   572→- salinity: preserve method and unit (e.g. dS/m) because measurement method matters;
   573→- yield: value + commodity-specific unit + moisture/content basis where relevant;
   574→- price/cost: amount + ISO currency code + date + market/source.
   575→
   576→Create a versioned data dictionary. Never convert values without preserving the source unit, conversion factor, and conversion version.
   577→
   578→## 16. Data Quality, Coverage, and Uncertainty
   579→
   580→Do not compress these concepts into one arbitrary confidence score. Represent them separately.
   581→
   582→### 16.1 Quality status
   583→
   584→Suggested statuses:
   585→- `valid`
   586→- `suspect`
   587→- `invalid`
   588→- `missing`
   589→- `estimated`
   590→- `not_assessed`
   591→
   592→### 16.2 Coverage status
   593→
   594→Suggested statuses:
   595→- `complete_for_period`
   596→- `partial`
   597→- `outside_provider_coverage`
   598→- `insufficient_spatial_support`
   599→- `missing`
   600→- `not_assessed`
   601→
   602→### 16.3 Evidence class
   603→
   604→Suggested classes:
   605→- direct field measurement;
   606→- farmer-reported record;
   607→- station observation;
   608→- satellite-derived estimate;
   609→- reanalysis/model estimate;
   610→- global soil prediction;
   611→- curated agronomic reference;
   612→- synthetic test data.
   613→
   614→### 16.4 Uncertainty
   615→
   616→- Preserve source prediction intervals or ensemble spread when provided.
   617→- If uncertainty is unavailable, store `unknown`, not zero.
   618→- Do not invent probabilistic confidence values.
   619→- For derived features, describe uncertainty propagation method or mark it unquantified.
   620→- Distinguish measurement uncertainty, model uncertainty, spatial representativeness uncertainty, and missing-data uncertainty where possible.
   621→
   622→### 16.5 Field Data Passport
   623→
   624→Build a dedicated **Field Data Passport** for each field. It should show:
   625→- available variables;
   626→- missing variables;
   627→- source/product and version;
   628→- time period covered;
   629→- native spatial and temporal resolution;
   630→- last retrieval date;
   631→- data age/freshness;
   632→- proportion of valid pixels/observations;
   633→- observed vs estimated vs synthetic status;
   634→- unresolved warnings;
   635→- which analytical features are enabled/disabled as a result.
   636→
   637→This is a key product feature: users should understand whether the field has enough evidence for a given analysis before receiving a rotation comparison.

  1195→## 18. Feature Engineering Framework
  1196→
  1197→Create a feature registry rather than scattering formulas across services.
  1198→
  1199→Each feature definition must contain:
  1200→- feature code;
  1201→- display name and description;
  1202→- input variable codes;
  1203→- formula or algorithm reference;
  1204→- unit;
  1205→- temporal support;
  1206→- spatial support;
  1207→- minimum data coverage;
  1208→- quality requirements;
  1209→- missing-input behavior;
  1210→- version;
  1211→- evidence/source reference where the formula is agronomic.
  1212→
  1213→### 18.1 Environmental feature candidates
  1214→
  1215→- seasonal rainfall total;
  1216→- monthly rainfall climatology;
  1217→- rainfall anomaly against a declared baseline;
  1218→- number and duration of dry spells under a configurable definition;
  1219→- mean/min/max temperature;
  1220→- growing-degree days only when crop-specific base/upper thresholds are sourced;
  1221→- heat-stress days relative to crop/phenological thresholds with regional validity;
  1222→- frost exposure only where the data and crop thresholds support it;
  1223→- reference evapotranspiration ET0;
  1224→- soil-moisture anomaly by depth and product;
  1225→- vegetation index summaries where an imagery provider is implemented;
  1226→- bare-soil-window evidence from crop records/calendar and, when available, remote-sensing indicators.
  1227→
  1228→Do not calculate NDVI from data that do not include the required reflectance bands. Do not infer crop type from NDVI alone.
  1229→
  1230→### 18.2 Soil and agronomic features
  1231→
  1232→- pH status relative to crop-specific reference ranges;
  1233→- texture class from valid sand/silt/clay values;
  1234→- organic-carbon history;
  1235→- salinity status where measurement methods are known;
  1236→- soil-water holding proxies only when required parameters are available;
  1237→- crop-family diversity;
  1238→- crop sequence history;
  1239→- nitrogen input/output budget where inputs and outputs are sufficiently documented;
  1240→- cover duration;
  1241→- erosion susceptibility indicators only with a documented method and adequate terrain/rainfall/soil inputs.
  1242→
  1243→### 18.3 Missing data behavior
  1244→
  1245→If a feature cannot be computed, store a missing result with a reason code. Examples:
  1246→- `MISSING_REQUIRED_VARIABLE`
  1247→- `INSUFFICIENT_TEMPORAL_COVERAGE`
  1248→- `SPATIAL_RESOLUTION_TOO_COARSE`
  1249→- `UNVERIFIED_CROP_PARAMETER`
  1250→- `UNSUPPORTED_REGION`
  1251→- `INVALID_UNIT`
  1252→
  1253→Never use zero as a synonym for unknown.

  1255→## 19. Crop Rotation Candidate Generation and Optimization
  1256→
  1257→### 19.1 Inputs
  1258→
  1259→- field area and boundary;
  1260→- planning horizon and season definitions;
  1261→- current and previous crop history;
  1262→- crop catalog and variety information;
  1263→- regional calendars;
  1264→- crop traits and water parameters;
  1265→- soil observations/estimates;
  1266→- climate and water features;
  1267→- farm constraints;
  1268→- farmer objective weights;
  1269→- validated pest/pathogen rotation rules;
  1270→- equipment, labor, market, and storage constraints where supplied.
  1271→
  1272→### 19.2 Baseline scenario
  1273→
  1274→Always include the existing rotation or farmer-entered baseline. If the history is incomplete, clearly label the baseline as partial/incomplete. Do not invent a historical sequence.
  1275→
  1276→### 19.3 Candidate generation
  1277→
  1278→Generate a candidate crop set using transparent filters:
  1279→- crop data available for the relevant region;
  1280→- crop calendar does not conflict with the planning window;
  1281→- crop traits satisfy the user's stated constraints where known;
  1282→- soil/environment evidence does not indicate a clearly disqualifying condition;
  1283→- crop parameters required for objective calculation exist.
  1284→
  1285→A crop with insufficient evidence may appear in an exploratory list only if clearly labelled `NEEDS_LOCAL_REVIEW`; it must not silently enter the validated recommendation set.
  1286→
  1287→### 19.4 Hard constraints
  1288→
  1289→Examples:
  1290→- at most one primary crop per field/season unless intercropping is explicitly modeled;
  1291→- sowing and harvest windows must fit the planning horizon;
  1292→- crop duration must fit the selected calendar window;
  1293→- seasonal irrigation demand must not exceed an explicitly supplied water allocation when this is a hard constraint;
  1294→- excluded crops must not be selected;
  1295→- equipment/labor/market constraints must be honored if marked hard;
  1296→- pest/pathogen break rules only apply when the rule has valid regional scope and adequate evidence;
  1297→- soil and salinity restrictions only apply when required measurements/estimates are available and the rule is validated.
  1298→
  1299→Unknown constraints must not be interpreted as satisfied. Return `not_evaluated` where necessary.
  1300→
  1301→### 19.5 Soft objectives
  1302→
  1303→Support objective criteria such as:
  1304→- lower modeled irrigation requirement;
  1305→- improved crop-family diversity;
  1306→- contribution to nitrogen cycling where evidence supports the estimate;
  1307→- reduced bare-soil duration;
  1308→- lower erosion susceptibility under documented assumptions;
  1309→- potential gross margin or contribution margin where market data are provided;
  1310→- crop calendar flexibility;
  1311→- resilience under selected stress scenarios;
  1312→- risk diversification across crops.
  1313→
  1314→Do not equate legume presence with a fixed nitrogen gain. The amount of nitrogen fixation depends on species, variety, biomass, inoculation, soil, management, and residue handling.
  1315→
  1316→### 19.6 Optimization method
  1317→
  1318→Use Google OR-Tools CP-SAT for discrete sequencing and constraints. Keep the solver behind an `OptimizationSolver` interface.
  1319→
  1320→Model decisions as binary or integer variables for crop/season/management choices. Use integer-scaled coefficients for CP-SAT objectives, document the scaling, and test rounding behavior.
  1321→
  1322→For multiple objectives, produce a set of non-dominated or trade-off solutions using a documented method such as repeated epsilon-constraint solves or carefully defined weighted runs. Do not imply that one weighted sum captures every possible Pareto solution.
  1323→
  1324→Persist:
  1325→- solver status;
  1326→- runtime;
  1327→- optimality/bound details when available;
  1328→- objective coefficients and normalization rules;
  1329→- input snapshots;
  1330→- solver/library version;
  1331→- all hard-constraint outcomes.
  1332→
  1333→### 19.7 Scoring and ranking
  1334→
  1335→Do not produce an overall score when required criteria are missing or incomparable. When a score is permitted:
  1336→- normalize each objective using fixed/source-defined or declared reference ranges;
  1337→- disclose directionality (higher/lower is better);
  1338→- preserve raw values next to normalized values;
  1339→- apply farmer weights transparently;
  1340→- show criterion coverage;
  1341→- make missing criteria visible rather than silently filling them;
  1342→- avoid comparing incomparable units without a documented normalization.
  1343→
  1344→### 19.7.1 Soil-health objective guardrail
  1345→
  1346→The optimizer must not treat a generic soil-health score as a physically measured quantity. Implement soil-related objectives as explicit, separately reported indicators or evidence-backed proxies (for example, cover duration, crop-family diversity, or a documented nutrient-balance estimate). If the available data do not support a defensible soil-health objective for a field, mark that objective as unavailable and do not let a fabricated composite score influence the ranking. Any later composite index must have a published definition, weights, regional validity, sensitivity analysis, and agronomist review.
  1347→
  1348→### 19.8 Output status vocabulary
  1349→
  1350→Use statuses such as:
  1351→- `feasible`;
  1352→- `infeasible`;
  1353→- `not_evaluated`;
  1354→- `needs_local_review`;
  1355→- `insufficient_data`;
  1356→- `candidate_only`;
  1357→- `approved_by_advisor`.
  1358→
  1359→A strategy must never be labelled “best” without specifying the objective context and evidence limitations.
  1360→
  1361→## 20. Water Intelligence Engine
  1362→
  1363→### 20.1 Main concept
  1364→
  1365→Use the FAO-56 crop coefficient approach where inputs and crop parameters are available:
  1366→
  1367→`ETc = Kc × ET0`
  1368→
  1369→ET0 is reference evapotranspiration; Kc varies with crop and development stage. The implementation must preserve whether the input is single-Kc or dual-Kc. Do not assume a constant Kc across the whole season where stage-specific coefficients are available or required.
  1370→
  1371→### 20.2 Water balance
  1372→
  1373→Implement a clearly documented, configurable water-balance calculation. A simplified root-zone accounting form may be used only when its assumptions are explicit:
  1374→
  1375→`Net irrigation need = max(0, ETc - effective_rainfall - usable_soil_water_change - capillary_rise_contribution)`
  1376→
  1377→where terms are defined with consistent signs and units. If soil-water storage, effective rainfall, capillary rise, runoff, deep percolation, salinity leaching, or other terms are unavailable, do not pretend the simplified estimate is a complete irrigation prescription.
  1378→
  1379→Gross applied irrigation may be approximated as net irrigation divided by application efficiency only when a defensible efficiency value is provided or explicitly assumed and shown.
  1380→
  1381→### 20.3 Required outputs
  1382→
  1383→- crop ET estimate by growth stage and period;
  1384→- rainfall contribution estimate and method;
  1385→- estimated net irrigation requirement;
  1386→- gross irrigation estimate only when efficiency inputs exist;
  1387→- water allocation versus estimated requirement;
  1388→- water deficit/surplus by period;
  1389→- missing inputs and assumptions;
  1390→- uncertainty or range where supported;
  1391→- comparison across rotation scenarios.
  1392→
  1393→### 20.4 Additional controls
  1394→
  1395→- keep units consistent (mm, m3, ha);
  1396→- convert 1 mm over 1 hectare to 10 m3 correctly;
  1397→- do not confuse ET with withdrawal or applied irrigation;
  1398→- account for irrigation method and efficiency only if available;
  1399→- consider salinity/leaching requirements separately and only with appropriate local evidence;
  1400→- do not issue real-time irrigation instructions without validated local sensor/field inputs and expert-approved thresholds.
  1401→
  1402→## 21. Soil Health Ledger
  1403→
  1404→Build an indicator-based ledger rather than one opaque “soil health score.”
  1405→
  1406→Track, where data exist:
  1407→- soil organic carbon / organic matter;
  1408→- pH;
  1409→- electrical conductivity/salinity;
  1410→- texture;
  1411→- bulk density;
  1412→- total nitrogen and nutrient measurements;
  1413→- soil moisture;
  1414→- cover duration;
  1415→- management events;
  1416→- crop-family diversity;
  1417→- erosion-related indicators.
  1418→
  1419→Every value must identify whether it is:
  1420→- measured by a laboratory;
  1421→- reported by the farmer;
  1422→- estimated from a gridded model;
  1423→- calculated from a transparent nutrient budget;
  1424→- inferred from a remote-sensing product.
  1425→
  1426→The ledger must show trends only when repeated comparable measurements exist. Warn when sampling depth, season, laboratory method, or analytical units differ. Never claim a measured increase in soil organic carbon based solely on a management event or a one-season model estimate.
  1427→
  1428→### Nutrient budget
  1429→
  1430→A later module may calculate partial nutrient balances using measured/recorded inputs and outputs. It must expose uncounted pathways and uncertainties. Biological nitrogen fixation, residue mineralization, leaching, gaseous losses, and crop uptake cannot be assumed as fixed constants without appropriate evidence.
  1431→
  1432→## 22. Climate Stress Testing Lab
  1433→
  1434→Separate stress testing from forecasting.
  1435→
  1436→### Scenario types
  1437→- historical reference period;
  1438→- user-defined rainfall reduction/increase;
  1439→- user-defined temperature shift;
  1440→- water-allocation reduction;
  1441→- shifted season timing;
  1442→- combined heat and drought;
  1443→- selected climate-projection dataset scenario when added later.
  1444→
  1445→Every result must state that a user-defined perturbation is a hypothetical scenario, not a forecast.
  1446→
  1447→### Sensitivity analysis
  1448→
  1449→Start with deterministic sensitivity analysis (for example, a range of rainfall and water allocation changes). Add Monte Carlo only when suitable distributions and dependencies can be justified from data.
  1450→
  1451→If using stochastic simulations:
  1452→- set and persist random seeds;
  1453→- preserve observed dependence/correlation among climate variables where possible;
  1454→- do not independently randomize variables when this creates physically implausible combinations;
  1455→- report distributions and intervals, not a false precise probability;
  1456→- make model assumptions visible.
  1457→
  1458→### Output metrics
  1459→- feasibility under scenario;
  1460→- estimated water deficit;
  1461→- crop stress indicator where model supports it;
  1462→- changes in objective values;
  1463→- relative ranking stability;
  1464→- failure points and threshold crossings;
  1465→- data/model limitations.
  1466→
  1467→## 23. Bare Soil Window and Cover-Crop Planner
  1468→
  1469→Calculate candidate bare-soil windows using crop history, crop calendars, sowing/harvest dates, and management records. Remote-sensing evidence may be added when an appropriate product is implemented.
  1470→
  1471→The planner should:
  1472→- estimate the gap between harvest and next sowing;
  1473→- report the evidence used to estimate bare-soil duration;
  1474→- identify cover-crop candidates only when regional calendar, water, and agronomic data support them;
  1475→- assess whether a cover crop could compete for scarce water before the next cash crop;
  1476→- include termination timing and equipment constraints;
  1477→- avoid suggesting cover crops in windows that are operationally or climatically unsuitable.
  1478→
  1479→## 24. Pest and Disease Rotation Intelligence
  1480→
  1481→Build a curated, evidence-backed rule engine first. A full knowledge graph is optional later.
  1482→
  1483→A rule should contain:
  1484→- pest/pathogen identifier;
  1485→- affected host crops and varieties where known;
  1486→- relevant crop families where evidence supports it;
  1487→- region/season/soil/climate applicability;
  1488→- break-period guidance and its source;
  1489→- management/context dependencies;
  1490→- severity and confidence/evidence status;
  1491→- source citation;
  1492→- agronomist review state.
  1493→
  1494→Rules without region-specific validity must be warnings for review, not hard constraints. Do not generalize disease cycles based only on botanical family.
  1495→
  1496→## 25. Farm Memory and Learning Loop
  1497→
  1498→Record:
  1499→- planned crops and dates;
  1500→- actual planting/harvest dates;
  1501→- irrigation and input quantities;
  1502→- management events;
  1503→- pest/disease events;
  1504→- observed weather impacts;
  1505→- actual yield and quality;
  1506→- costs and selling prices where supplied;
  1507→- farmer feedback and reasons for plan changes.
  1508→
  1509→The comparison engine should show planned versus actual outcomes. Historical recommendations must remain immutable and versioned. Any future personalization or model calibration must be explicit, validated, consent-aware, and reversible.
  1510→
  1511→Do not automatically train models on user records. Add an opt-in data contribution and privacy policy before any aggregated learning workflow.
  1512→
  1513→## 26. Explainability and Evidence Engine
  1514→
  1515→Every scenario must have structured explanation records.
  1516→
  1517→Each explanation should answer:
  1518→- Why was this crop/rotation considered?
  1519→- Which constraints were evaluated?
  1520→- Which were satisfied, violated, or not evaluated?
  1521→- Which observations and crop-knowledge sources influenced the result?
  1522→- Which benefits are potential rather than measured?
  1523→- What risks or trade-offs remain?
  1524→- What inputs are missing?
  1525→- What needs local review?
  1526→
  1527→Store evidence references, rule IDs, feature IDs, and algorithm versions. Do not rely on free-form LLM text as the sole evidence record.

  1936→
  1937→- Use calm, accessible, high-contrast colors; do not rely on red/green alone to communicate status.
  1938→- Use plain language in Farmer Mode.
